# Подключение сайта привилегий к игровому серверу

Документ для того, кто собирает сервер. Всё, что нужно сделать со сборки
стороны, — здесь; читать код сайта не требуется.

Сайт уже работает: <https://zm.hotcs.ru>. Он продаёт привилегии и
кредиты, ведёт панель выдачи и пишет привилегии в MySQL. Игровой сервер должен
начать читать их **оттуда**, а не из `users.ini`.

Исходники сайта — в `site/`, эксплуатационные подробности — в
`site/README.md` и `site/server-side/README.md`.

---

## Зачем вообще что-то менять

У привилегии появился **срок действия**. В `users.ini` его хранить негде: формат
из четырёх полей, даты в нём нет. А в AMX Mod X 1.10 штатный плагин админов
собран **дважды** — обычный и SQL-вариант, — и SQL-вариант выполняет ровно один
запрос, **без условий**:

```
SELECT auth, password, access, flags FROM <amx_sql_table>
```

Условий нет — значит их можно спрятать внутрь. На стороне базы `zm_admins` —
не таблица, а **представление**, которое само отбрасывает просроченные записи.
Ни плагина, ни задачи по расписанию не нужно: срок обеспечивает база.

Проверить можно по исходнику, он лежит в проекте:
`upstream/reference/amxx-1.10.0-git5479/addons/amxmodx/scripting/admin.sma`,
функция `adminSql()`.

## Правка 1. Переключить плагин админов

`configs/plugins.ini` **собирается** `tools/assemble.mjs` (раздел
«конфигурация»), поэтому править готовый файл в `server/` бесполезно — он
перезапишется. Менять надо в `assemble.mjs`, там же, где он уже правит
`modules.ini`.

Нужно, чтобы в собранном `plugins.ini` вместо

```
admin.amxx		; admin base (required for any admin-related)
;admin_sql.amxx		; admin base - SQL version (comment admin.amxx)
```

получилось

```
;admin.amxx		; admin base (required for any admin-related)
admin_sql.amxx		; admin base - SQL version (comment admin.amxx)
```

Например так:

```js
// Админов берём из базы сайта, а не из users.ini: только так у привилегии
// появляется срок действия — просроченная запись просто перестаёт попадать в
// выборку. Загружать надо РОВНО ОДИН из двух: это один и тот же плагин,
// собранный с #define USING_SQL и без него.
cur = cur
  .replace(/^admin\.amxx/m, ';admin.amxx')
  .replace(/^;admin_sql\.amxx/m, 'admin_sql.amxx')
```

### Почему это не может запереть владельца снаружи

SQL-вариант, не достучавшись до базы, **сам читает `users.ini`**:

```pawn
if (sql == Empty_Handle)
{
    server_print("[AMXX] %L", LANG_SERVER, "SQL_CANT_CON", error)

    //backup to users.ini
    ...
    loadSettings(configsDir) // Load admins accounts
    return PLUGIN_HANDLED
}
```

Упал сайт, легла база, ошиблись в пароле — сервер ведёт себя ровно как сейчас.
Поэтому правку можно вносить до того, как база настроена, и держать в
`custom/admins.ini` учётку владельца как запасной вход.

⚠️ Проверьте `tools/verify-ru.mjs`: он читает порядок загрузки из собранного
`plugins.ini`. Если он ждёт там `admin.amxx` — поправьте ожидание.

## Правка 2. Прописать базу в `configs/sql.cfg`

Готовый файл с пояснениями — `site/server-side/sql.cfg`. Реквизитов в нём нет
намеренно: это git-репозиторий, и пароли сюда не кладут (по той же причине из
него исключён `custom/admins.ini`). Настоящие значения — у владельца, они же
лежат на хостинге в `/private/config.php`, раздел `db`.

```
amx_sql_host    "95.213.255.80"
amx_sql_user    "<отдельный пользователь, только SELECT>"
amx_sql_pass    "<...>"
amx_sql_db      "<база сайта>"
amx_sql_table   "zm_admins"
amx_sql_type    "mysql"
amx_sql_timeout "5"
```

⚠️ **`amx_sql_table` — именно `zm_admins`.** По умолчанию плагин ищет `admins`,
но таблица с таким именем в этой базе **уже занята** соседним сайтом. И это не
`zm_privileges`: в `zm_privileges` лежат в том числе просроченные записи, и
направив плагин туда, вы сделаете все привилегии вечными.

⚠️ **Пользователь MySQL нужен отдельный, с правом только `SELECT`** на
`zm_admins`. У сайта пользователь с полными правами на базу; его пароль в
`sql.cfg` на игровом хостинге — это полный доступ к заказам и игровым паролям
для всех, кто видит файлы игрового сервера.

```sql
GRANT SELECT ON `база`.`zm_admins` TO 'игровой_пользователь'@'%';
```

### Как вышло на деле (2026-08-11)

Владелец завёл **отдельную базу `s2676_zmcs16`** (тот же хост 95.213.255.80) и
решил держать в ней и сайт, и сервер — чтобы не разводить две. Поэтому:

* доступ лежит в `custom/db.ini` (вне репозитория), `sql.cfg` собирается из него;
* схема сайта применена туда же: `node tools/mysql.mjs --file site/sql/schema.sql`;
* рядом с ней живут игровые таблицы `zm_progress`, `zm_knife`, `zm_skin`,
  `zm_stats` — сайт может читать их напрямую, ходить к серверу не нужно;
* пользователь у обоих пока ОДИН, с полными правами на эту базу. Разделить их
  по-прежнему стоит: игровому серверу хватит `SELECT` на `zm_admins` и записи в
  четыре игровых таблицы.

⚠️ **Игровые таблицы — двоичные (`VARBINARY`), и это нарочно.** Модуль MySQL в
AMXX соединяется как latin1: в столбцах `utf8mb4` кириллица легла бы двойной
кодировкой (`Ð½Ð¸Ðº:eugen`), и сайт читал бы кракозябры. У двоичных столбцов
байты не трогает никто — обе стороны видят настоящий UTF-8. По той же причине
`zm_admins` отдаёт `auth` и `password` через `CAST(... AS BINARY)`.

⚠️ **Проверено вживую:** «Загружен 1 администратор из базы данных» в консоли
сервера, привилегия на ник «Игорь» доехала целой.

`localhost` в `amx_sql_host` не писать: клиент MySQL пойдёт искать файл-сокет,
которого на другой машине нет.

## Правка 4 (только если продаются кредиты)

Сайт умеет начислять кредиты после оплаты, но **штатной командой это делать
нельзя**. `zp_packs` из `custom/plugins/zp_shop_weapons.sma` вызывает

```pawn
zp_set_user_ammo_packs(target, amount)
```

то есть **устанавливает** баланс, а не прибавляет к нему: покупка стёрла бы
всё, что игрок заработал за вечер. Прочитать баланс снаружи тоже нечем —
`zp_progress_show` печатает только ключи и признак загрузки.

Нужна команда-прибавка. Готовый код (регистрация + обработчик `cmd_packs_add`)
лежит в `site/server-side/README.md`, раздел 4. После неё на сайте включается
`'shop' => array('packs_command' => 'zp_packs_add')`.

⚠️ Текст ответа `игрок «%s» не найден` менять нельзя, не поправив
`deliver_packs()` на сайте: по нему сайт понимает, что игрок вышел, и оставляет
заказ ждать в панели.

## Что сайт кладёт в базу

Таблица `zm_privileges`, одна строка на игрока:

| столбец | смысл |
|---|---|
| `auth` | ник как в игре либо `STEAM_0:1:12345` |
| `auth_key` | тот же ключ со свёрнутой **латиницей**; уникален |
| `password` | игровой пароль |
| `access` | буквы уровня (`t`/`s`/`q`/`p`/`o`) плюс буквы купленной админки |
| `account` | флаги записи AMXX: `a`, `ce`, `e` |
| `expires_at` | `NULL` — навсегда |

Представление отдаёт серверу только непросроченное и переименовывает `account`
в `flags` — плагин ищет столбцы **по именам**, через `SQL_FieldNameToNum()`:

```sql
CREATE OR REPLACE VIEW `zm_admins` AS
  SELECT `auth`, `password`, `access`, `account` AS `flags`
  FROM `zm_privileges`
  WHERE `expires_at` IS NULL OR `expires_at` > NOW();
```

### Про свёрнутый ключ

`admin.sma` сверяет ключи через `equali()`, а это `strncasecmp` по байтам:
регистр складывается **только у латиницы**. Значит «Vasya» и «vasya» для сервера
один игрок, а «Игорь» и «игорь» — разные. Уникальность в базе стоит на
`auth_key`, свёрнутом ровно так же. Это не теория: на проверке сайт завёл две
записи на одного игрока, и сервер взял бы не ту, что оплачена.

## Что изменилось 12 августа 2026

Две правки, которые касаются сборки. Обе уже внесены в файлы проекта — ниже
только объяснение, чтобы они не выглядели чужими и не были откачены.

**Домен сменился на `zm.hotcs.ru`.** Прежнего `pw792.castledev.ru` нет уже и в
DNS — перенаправлять с него нечего.

**Раздача файлов игрокам ушла с веб-хостинга.** Владелец решил держать её на
игровом хостинге и освободить место: дерево `cstrike/` весило около 260 МБ и
удалено. Поэтому в `custom/server-extra.cfg` теперь

```
sv_downloadurl ""
```

и **перед запуском сервера сюда надо вписать адрес раздачи игрового хостинга**.
Пустая строка — это встроенная закачка GoldSource по 20 КБ/с: двести мегабайт
качаются часами, и новичок уходит, не дождавшись. Ошибки он не увидит — игра
молча пустит его без моделей, так что проверять только заходом с чистого
клиента. Адрес нужен **без TLS и без перенаправлений**: движок не умеет ни
того, ни другого. Дерево для заливки собирается командой
`node tools/build-fastdl.mjs` и лежит в `dist/fastdl`.

**Классы зомби переразложены по уровням** — так попросил владелец:

| Класс | Было | Стало |
|---|---|---|
| Спринтер | VIP | VIP |
| Ганимед | Император | **VIP** |
| Шаман | Лидер | Лидер |
| Ревенант Огонь | Фараон | **Лидер** |
| Ревенант Лёд | Фараон | **Император** |
| Ревенант Яд | Создатель | **Фараон** |

Правится это в трёх местах, и все три обязаны совпадать:

* `custom/plugins/zp_zclass_vip.sma`, массив `g_foreign_flag` — там охрана: класс
  не по уровню возвращается к обычному в момент заражения;
* `zclass_info` в самом плагине класса (`custom/plugins/cso_class_*.sma`) — это
  вторая строка пункта меню, игрок читает уровень именно там;
* `site/private/app/catalog.php` — витрина сайта.

Разойдутся — игрок купит уровень ради класса и получит отказ в игре.

Раскладка намеренно **не растёт по здоровью**: у Императора свой класс (3400)
слабее уже открытого ему по Лидеру (3600). Это не ошибка — флаги накопительные,
старший уровень получает всё, что есть у младших, и сильный класс никуда не
девается.

## Чего менять НЕ надо

* `zp_vip.sma`, `zp_skins.sma`, `zp_knives.sma` — читают `get_user_flags()` и не
  знают, откуда взялся админ;
* уровни, буквы флагов, числа наград — сайт повторяет их у себя
  (`site/private/app/tiers.php`) и обязан совпадать. Меняете `g_tiers` —
  скажите, поправлю там же;
* `custom/admins.ini` и локальная панель `admin.cmd` — остаются как запасной
  вход, именно их сервер прочитает при недоступной базе.

## Как убедиться, что сработало

1. В панели сайта (`/admin/`) выдать себе VIP на 30 дней.
2. В логе игрового сервера при старте карты — `Loaded N admins from database`.
   Если там `SQL_CANT_CON`, сервер не дотянулся до базы: чаще всего хостинг
   режет исходящий 3306 либо пользователь заведён без `@'%'`.
3. Зайти на сервер, в консоли `setinfo _pw "выданный_пароль"`.
4. `amx_who` в консоли сервера — должны быть флаги уровня.
5. Поставить `expires_at` в прошлое, сменить карту — прав больше нет.

## Что нужно от владельца

Без этого сайт работает, но вполсилы:

* **ip:port игрового сервера и `rcon_password`** → в `/private/config.php`,
  раздел `rcon`, и `enabled => true`. Тогда права появляются через секунду, а не
  со сменой карты. RCON здесь ускоритель, а не несущая конструкция: без него
  всё доедет само;
* **отдельный пользователь MySQL** только на чтение `zm_admins`;
* **ключи кассы**, если нужна автоматическая оплата.
